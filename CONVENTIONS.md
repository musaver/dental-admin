# Conventions

The rules this codebase depends on that the database schema cannot express.
Every one of these was a deliberate decision; breaking one corrupts data
silently, because there are **no foreign keys, no CHECK constraints and no
triggers** anywhere in the schema.

## Time

- **MySQL `DATETIME` columns hold naive clinic-local wall clock.** An
  appointment at 09:00 is stored as `09:00` and means 09:00 at the clinic.
- `lib/db.ts` pins the pool to `timezone: 'Z'` so mysql2 maps those digits into
  a `Date`'s UTC fields identically on every machine. Without it, the same row
  reads five hours apart between Vercel (UTC) and a dev Mac (PKT).
- **Read stored dates only with `getUTC*` accessors** — in practice, only
  through `lib/datetime.ts`. `toLocaleString()`, `getHours()` or date-fns on a
  stored value shifts it by the viewer's timezone.
- The clinic timezone is `Asia/Karachi` (`CLINIC_TIMEZONE`), one zone
  nationwide, no daylight saving. `SUPPORTED_TIMEZONES` is deliberately a
  single-entry list.
- `staff_schedules.dayOfWeek`: **0 = Sunday … 6 = Saturday**, matching
  `Date.getUTCDay()`. Display weeks start Monday; the two are independent.

## Money

- **Every monetary column is `int` holding WHOLE PKR.** Never divide by 100.
  Confirmed against the seeded price list (Consultation 1000, RCT-Molar 22000).
- **`payments.amount` is always positive; direction lives in `payments.type`.**
  A refund is a `type='refund'` row. Nothing may sum `amount` raw — use
  `signedAmount()` / `sumPayments()` from `lib/money.ts`.
- **Invoice totals invariant:** `totalAmount === Σ(line amounts)`, where a
  discount line carries a negative amount and per-line discounts are counted
  once. `assertInvoiceTotals()` enforces it before any write.
- There is **no balance column**; balance is always
  `totalAmount − paidAmount`. `payments.invoiceId` is nullable, so a patient's
  real balance must also subtract unallocated credit — see `lib/ledger.ts`.
- `invoices.paidAmount` and `status` are denormalised. Every payment write goes
  through `recomputeInvoice()` **inside the same transaction**. A waived
  invoice stays waived; a fully refunded one reads `refunded`.

## Identity

- **MRN:** `MAIN-000123` — branch code + zero-padded per-branch sequence.
  Generated by `nextMrn()` inside the insert transaction, retried on
  errno 1062. The padding makes `ORDER BY mrn DESC` numeric.
- **A patient row is built by `insertPatient()`** (`lib/patient-registration.ts`),
  which mints the MRN, normalises every phone number and joins the caller's
  transaction. Registration and booking-a-new-patient both go through it; lead
  conversion is the one remaining hand-built copy.
- **Which branch registers a patient is `resolveWritingBranch()`**, not
  `resolveBranchScope()`. Head office must name one — there is no default,
  because guessing files a whole clinical history under the wrong clinic.
- **Invoice numbers:** `INV-MAIN-2608-00042` — per branch, resetting monthly.
  Same transactional/retry pattern (`allocateInvoiceNumber()`).
- **Phone numbers** are normalised to `+92XXXXXXXXXX` on every write
  (`normalizePhone()`), because phone is the only required contact field and
  what duplicate detection keys on.
- **Tooth numbers are FDI two-digit** (11–48 permanent, 51–85 primary). `32`
  is the lower-left lateral incisor, *not* the Universal-system third molar.
  `surfaces` is a packed string (`"MOD"`) in canonical order; `teeth` is a CSV.
  Only `lib/odontogram.ts` interprets these encodings.

## Denormalised fields (eight) and pointer pairs (five)

Recompute helpers in `lib/derive.ts` are the **only** writers for:
`patients.hasAlerts`, `invoices.paidAmount`, `invoices.status`,
`treatment_plans.{totalAmount,discountTotal,netAmount}`,
`treatment_plan_items.netAmount`.

`discount_codes.usedCount` is the eighth, and the one exception to that rule:
its live writer is the conditional `UPDATE` in `lib/discount-codes.ts`, because
only a single guarded statement can enforce a usage limit against concurrent
redemption — a recompute-from-source would let two transactions count the same
rows and both write N+1. `recomputeDiscountCodeUsage()` is the repair path, and
`check:invariants` detects drift against the invoices that redeemed it.

Bidirectional pairs are written both-sides-in-one-transaction, via the helpers
in `lib/derive.ts` / `lib/recalls.ts`:

- `leads.convertedPatientId` ↔ `patients.leadId`
- `appointments.treatmentPlanItemId` ↔ `treatment_plan_items.appointmentId`
- `appointments.recallId` ↔ `recalls.appointmentId`
- `tooth_conditions.treatmentPlanItemId` ↔ `treatment_plan_items.toothConditionId`
- `treatment_plan_items.visitProcedureId` ↔ `visit_procedures.treatmentPlanItemId`

`npm run check:invariants` detects drift in all of them.

## Authorisation

- **`requirePermission()` is the boundary, not the JWT.** It re-reads
  `admin_users.isActive` and the role's permissions on every call (5-second
  cache), which is what makes deactivation take effect on the next request.
- Middleware is Edge-only routing: it verifies the token signature and the
  `kind` claim (staff vs patient) and **must never query the database**.
- The 31 permission slugs in `lib/permissions.ts` are exactly what the seeded
  roles store. `admin_roles.permissions` is a `text` column — always parse
  through `parsePermissions()`, which tolerates a malformed row.
- **No owner bypass.** The Admin/Owner role holds all 31 slugs explicitly.
- 24 tables have no `branchId`. Any route touching one goes through a loader in
  `lib/loaders.ts`, which resolves the owning patient/plan/invoice and checks
  the branch. Not-found and not-yours are both **404**.
- Portal rules: no portal route accepts a `patientId` from the client; linked
  patients come from the session and filter in the WHERE clause; foreign rows
  are 404, never 403.

## Lifecycles

- Status strings and their parallel timestamps are **always written together**
  through `applyStatusChange()` (appointments) / `applyPlanStatusChange()`
  (treatment plans). Missing steps are backfilled so timelines have no holes.
- **No-show sets `status` only** — who marked it lives in `audit_logs`.
  `in_progress` has no timestamp; the linked visit's `createdAt` is when work
  started.
- Rescheduling **clears `reminderEmailSentAt`**, or the patient is only ever
  reminded about the old time.
- Once a treatment plan is accepted its **pricing is locked** — amendments are
  a new plan, so the agreed figure stays auditable.
- The odontogram is event-sourced: the chart is `status='active'` rows;
  resolving stamps `resolvedAt`, never deletes.
- Recall `overdue` is **derived in queries**, never stored.

## Records

- `audit_logs` is the medico-legal record: **never purged**, real before/after
  diffs, secrets redacted, `patientId` set on every patient-scoped entry.
  Chart opens, file downloads, exports and logins are recorded views.
  Audit writes are non-fatal and join the caller's transaction.
- `login_attempts` is telemetry: purged after 30 days by the daily cron.
- Staff and patients are **never hard-deleted** — deactivate / archive.
  ~15 tables reference them with no FKs; deletion orphans history.
- The full export streams NDJSON through per-table **column allowlists**
  (`lib/export-allowlist.ts`). The audit row is written before the stream
  opens. Three exports per person per day.

## Migrations

- `lib/schema.ts` is **hand-maintained** — regenerating it from the database
  loses 80 index definitions and every `$onUpdateFn`. Its header says so.
- Change flow: edit schema → `npm run db:generate` → **read the emitted SQL**
  (it must never contain `DROP TABLE`) → `npm run db:migrate`.
- `db:push` is named `db:push:DANGER` for a reason.

## Communication

- Only **email** actually sends. SMS/WhatsApp are loggable channels with no
  provider; do not promise them to the clinic.
- Every message goes through `sendTemplatedEmail()`: rendered from the code
  registry (DB overrides optional), logged to `communication_logs` with
  `templateKey` and `referenceType`/`referenceId`.
- **A missing email address is a `skipped` log row, not an error** — those
  rows are the front desk's call list.
- A patient's history includes pre-conversion messages via `patients.leadId`;
  the patientId-XOR-leadId invariant on `communication_logs` is never
  rewritten.

## Verification

`npm run check` runs everything: typecheck, 209 unit tests, then live-database
checks (relations, enums, RBAC, patients, plans, clinical chain, scheduling,
billing, leads, invariants). HTTP-level suites need the dev server:
`check:reminders`, `check:export`, `check:portal` (run with `EMAIL_DRY_RUN=1`).
Every script creates its own data and cleans up after itself.
